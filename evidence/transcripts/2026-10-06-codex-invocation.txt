## How this goal maps to m2

[GOAL.md](/work/GOAL.md:1) is useful source material, but it is not itself a runnable m2 plan. A runnable plan needs the prescribed filename, front matter, and body sections defined by [m2.protocol.md, “Plan-file minimum schema”](/plugin/references/m2.protocol.md:1457) and [m2-artifact-schemas.md, “Plan Front Matter Record”](/plugin/references/m2-artifact-schemas.md:27).

The goal exposes three packet domains:

- Backend export endpoint.
- Frontend download interaction.
- User-guide documentation.

These could become three M1 lanes if `numM1s:3` were explicitly requested and their scopes were safe. Otherwise m2 defaults to one M1 and could move the same packets serially. The lane rules are in [m2.protocol.md, “Delegated Management Contract”](/plugin/references/m2.protocol.md:444) and [m1.protocol.md, “Relationship to m2()”](/plugin/references/m1.protocol.md:213).

## Core planning and manager artifacts

1. **Acceptance matrix**

   The conductor would normalize the goal into atomic, source-traceable acceptance rows before dispatch. Likely rows would cover:

   - The signed-in user can request `GET /notes/export.csv`.
   - The export contains every note that user owns and no notes owned by others.
   - The response is streamed as CSV.
   - The notes-list button downloads that export.
   - The user guide states the export format and columns.
   - All three workstreams are on `main` with passing checks.

   Each row needs source inputs, target behavior, journey, gates, packet IDs, evidence, status, and blocking questions. This is defined by [m2.protocol.md, “Acceptance-First Planning Contract”](/plugin/references/m2.protocol.md:1559), [writeAC.protocol.md, “M2 acceptance module contract”](/plugin/references/writeAC.protocol.md:110), and [m2-artifact-schemas.md, “Acceptance Matrix Row Record”](/plugin/references/m2-artifact-schemas.md:60).

   The exact CSV columns, ordering, escaping, encoding, filename, and unspecified error behavior cannot be invented. Discovery must resolve them from the application, or the matrix must record blocking questions under [writeAC.protocol.md, “Transformation rules”](/plugin/references/writeAC.protocol.md:46).

2. **M1 manager output for each active lane**

   Backend, frontend, and docs ownership would each be represented by a manager summary containing owned packets, write and denied scopes, dependencies, contract decisions, implementation steps, prompts, validation, questions, and handoff. Defined in [m2.protocol.md, “Manager output schema”](/plugin/references/m2.protocol.md:3130).

   Each manager must finish with a dispatch-ready packet, an integration decision, or a concrete blocker. Worker-supervision rows also record deliverable, status, last/next check, and redirect action. See [m1.protocol.md, “Execution phases,” Phases 2–5](/plugin/references/m1.protocol.md:81).

3. **Canonical packet records**

   At minimum there would be backend, frontend, and docs packet rows, probably followed by integration/verification/delivery packets. Each names its manager, exact paths, denied paths, dependencies, acceptance IDs, tests, evidence, integration owner, rollback, and status artifact.

   Defined in [m2.protocol.md, “Canonical packet registry row”](/plugin/references/m2.protocol.md:3170) and [m2-artifact-schemas.md, “Packet Row Record”](/plugin/references/m2-artifact-schemas.md:111).

4. **File-lease records**

   These separate backend source/tests, frontend source/tests, and guide files, while identifying any shared files and integration order. Defined in [m2-artifact-schemas.md, “File Lease Record”](/plugin/references/m2-artifact-schemas.md:144).

5. **Interface-contract record**

   Because the frontend consumes a new backend route, the manager needs a shared contract covering the route, response fields, compatibility, defaults, errors, tests, consumers, and signoffs before dependent workers dispatch. Defined in [m2.protocol.md, “Interface Lock Gate”](/plugin/references/m2.protocol.md:1894) and [m2-artifact-schemas.md, “Interface Contract Record”](/plugin/references/m2-artifact-schemas.md:157).

6. **Worker/tester prompts and worker-output records**

   Prompts are part of the manager output and must carry bounded scopes, tests, acceptance IDs, and stop conditions. Returned work is recorded with branch, SHAs, diff, changed paths, commands, evidence, reviewer, and residual risk. Defined in [m2.protocol.md, “Worker output schema”](/plugin/references/m2.protocol.md:3206) and [m2-artifact-schemas.md, “Worker Output Record”](/plugin/references/m2-artifact-schemas.md:1241).
